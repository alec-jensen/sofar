# M2 SimpleFIN client, ingest, data discovery

Spec: S11 (dedupe, bank edits, vanished, hide), S13 (coverage, identity), S15, S19.2 (balance snapshots), S19.15, S19.24, S12a ("pending" subsection). Architecture: A7, A9.5, A10. Read first: `docs/discovery/PROBE.md`, `docs/discovery/known-facts.md`. Port from `git show main:server/simplefin.go` and `git show main:server/netguard.go` (already moved in M0).

**Goal:** a provider seam, a hardened SimpleFIN v2 client, an ingest pipeline that never loses user decisions, sync jobs within the request budget, and the probe report.

**Exit criteria:**
- Scheduled pulls are idempotent against fixtures (and against the live account, once the owner allows).
- `docs/discovery/report.md` exists, and amendments are filed for any divergence from the spec.
- A test proves every pull sends `pending=1`.
- **Owner gate:** the owner exports `SIMPLEFIN_ACCESS_URL` (a separate probe token, see `docs/plan/README.md` section 5). Without it, build against the public demo access URL and list what is blocked.

### [ ] M2.2 SimpleFIN v2 client (`internal/provider/simplefin`)
- Port `claim`, access URL parsing, the host allowlist and the outbound client (from `internal/netguard`). Requests always set `version=2` and **`pending=1`** (S15, ADR-0007), plus `start-date` and `end-date`, `account=` filters, and `balances-only=1` for balance refreshes.
- Parse `errlist`, falling back to the deprecated `errors` list, and the `connections` list. Classify errors:
  - `con.auth` and HTTP 403: auth failure
  - HTTP 402: subscription
  - the date-range message seen in `known-facts.md`: `window_warning`, which is **non-fatal**; record the size it recommends
  - quota: `quota`
- A token bucket (ADR-0020) persisted in the database (`provider_budget` rows with timestamps), so restarts cannot exceed the cap. On a quota warning, pause sync for 24 hours (S15) and notify.
- Reuse the fake SimpleFIN TLS server pattern from `git show main:server/integration_test.go` (`httptest.NewTLSServer` with claim, accounts, errlist and pending behaviors) as `internal/testkit/fakesimplefin`.

### [ ] M2.4 ingest pipeline (`internal/ingest`)
For each pulled account and transaction, in one database transaction per account batch:
1. **Account identity** (S13): match by (provider account id), else by (institution, name, mask) on re-link. Merge rather than duplicate.
2. **Upsert raw rows** by (account, provider id). Bank fields are immutable from the user's side. A **bank edit** to a posted row updates the bank columns in place, keeps the overlay, and records an `ingest.bank_edit` event with old and new values (S11).
3. **Id-rotation heal** (S11, S18a): if an incoming id is unknown, a stored row matches on (posted, amount, description, payee), and the stored id was **not** returned in the same response, re-key the stored row, keep its overlay and labels, and add a `txn_id_aliases` row.
4. **Fingerprint duplicate** (S11): the same (account, date, amount, normalized description) as another row with a different id is flagged "possible duplicate", never merged automatically.
5. **Pending** (S19.24): store pending rows. When a posted row arrives, reconcile it to the pending row by account, merchant, date window and amount tolerance (tips). Carry over the suggestion, labels and links, then retire the pending row. A pending row that never posts is dropped after a configurable period (default 14 days) with a note.
6. **Vanished** (S11): a stored posted row missing from a full-window response gets `missing_from_bank_at` and is kept and flagged, never deleted.
7. **Hidden tombstones** are never re-imported. **Closed accounts** (S13) keep their history, and their transactions still count; a disconnected account keeps the app running and shows a banner.
8. **Coverage** (S13): update `account_coverage` (earliest date, gaps) and mark months "partial" where a budget account lacks full coverage.
9. **Balance snapshots** (S19.2): store balance, available balance and balance date per pull.
10. Mark affected months dirty (the table exists from M3; until then write to `dirty_months` only).

### [ ] M2.5 sync jobs (`internal/sync`)
- `sync.scheduled`: about 06:00 and 18:00 home time, keyed `sync:2026-10-05T06`. Catch-up runs only the most recent missed slot, never a burst.
- `sync.manual`: 1-hour cooldown and about 6 a day (configurable). The response says when the next manual sync is allowed.
- **Window discovery** (S15): start with the size recommended by the last window warning (default 45 days, per `known-facts.md`), chunk requests by it, and never hardcode 90.
- **Gap recovery**: request from (last success minus 7 days). A gap larger than what the Bridge returns is marked "data gap" for that account.
- **Backfill**: walk backward in windows until a window comes back empty, spread over several days within the token bucket. A backfill in progress marks affected plans provisional.
- **Per-account status**: a partial failure keeps what succeeded. Retry only the failing account with an `account=` filter.
- **Auth failure**: a persistent banner state, a push notification, and a re-claim flow with a new setup token (S15).
- Write a `sync_runs` row per run with window, `requested_pending = true`, and the errlist.
- Tests: `TestS15_ScheduledTimesInHomeTZ`, `TestS15_ManualCooldownAndDailyCap`, `TestS15_GapRecoveryOverlapsSevenDays`, `TestS15_BackfillStopsOnEmptyWindow`, `TestS15_PartialFailureKeepsSuccessfulAccounts`, `TestS15_AuthFailureStartsReclaim`.
